    1. Project overview & your role

    The opening questions. Practise these out loud until they're smooth.

    Walk me through your project.Basic▸

    Luxe Screens is a booking website for private luxury theatres, used for birthdays, anniversaries, proposals and movie nights. A customer can:

    1. Browse theatres in a gallery (search, filter, sort, photo lightbox).
    2. Use the AI Experience Planner: enter occasion, budget and guests, and get a recommended theatre plus a cake/decor/gift package.
    3. Complete a 9-step booking: date & time → theatre → contact → occasion → cakes → decor → gifts → payment → receipt.
    4. Join a waitlist for upcoming cities.

    Technically it's three parts in one repository: a React 19 single-page app (Vite), a Node.js + Express REST API, and a shared package with the business rules both of them use. Data lives in PostgreSQL, accessed through Prisma. Everything is plain JavaScript.

    "It's a full-stack booking platform for private theatres: a React 19 frontend talking to an Express REST API backed by PostgreSQL. Users browse rooms, get a recommendation for their occasion, and book in nine steps with add-ons, coupons and a simulated payment. I built the database schema, the API, the booking logic and the whole UI."

    What was the most challenging part?Basic▸

    Tell it as a story: problem → why it's hard → what you did → result.

    Preventing double booking. Two customers can click "Pay" for the same theatre, slot and date at the same moment. A simple "check if free, then insert" has a race condition: both checks pass before either insert happens.

    I solved it at the database level. Each booking that holds a slot stores a key theaterId:slotId:date in a column with a UNIQUE constraint. The database rejects the second insert, and the API turns that error (Prisma code P2002) into a friendly 409 "slot just booked". Expired holds release the key by setting it to NULL; PostgreSQL allows many NULLs in a unique column.

    "The trickiest part was double booking. Instead of check-then-insert, which races, I put a unique constraint on an active-slot key so the database guarantees only one live booking per slot, and the API returns a 409."
    What would you improve if you had more time?Basic▸
    • Real payments (Razorpay/Stripe) with server-verified webhooks.
    • Authentication ("my bookings") and an admin panel for theatres, slots and coupons.
    • Email/SMS confirmations through a background queue.
    • Redis-based rate limiting, since the current limiter is in memory per server.
    • A scheduled job to expire stale holds (they expire lazily today).
    • TypeScript or at least // @ts-check with JSDoc, for compile-time safety as the code grows.
    • SEO: prerender the marketing pages, or add server rendering.
    • CI on GitHub Actions: lint, tests and build on every pull request.
    Naming limitations yourself shows maturity. Interviewers like candidates who know what their project doesn't do.

    What are npm workspaces, and why the shared package?Intermediate▸

    npm workspaces let one repository hold several packages (client, server, shared) with one npm install at the root. npm links shared into node_modules/@luxe/shared, so both apps import it like a normal package:

    import { calculatePrice } from "@luxe/shared/pricing";

    That lets the UI preview the price and validate forms with exactly the rules the server enforces. Without it I'd have to copy the code and keep two versions in sync.

    How does the frontend reach the API in development and in production?Intermediate▸

    • Production: the website (Vercel) and API (Render) are on different domains. The client prefixes calls with VITE_API_URL, and the API allows that origin through CORS (CLIENT_ORIGIN).

const API_BASE = (import.meta.env.VITE_API_URL ?? "").replace(/\/$/, "");

    What is Vite, and why use it?Basic▸

    Trace one booking request end to end.Intermediate▸
    1. User clicks Pay: payment-step.jsx calls apiFetch("/api/booking", { method: "POST", json: payload }).
    2. Vite proxy (dev) or VITE_API_URL (prod) sends it to Express.
    3. Express middleware: security headers → CORS → express.json() → rate limiter (10/min).
    4. The route validates the body with createBookingSchema.parse() (Zod) and calls createBooking().
    5. The service checks the date window and slot, prices the cart from the database, then in a transaction releases lapsed holds and inserts the booking.
    6. Response 201 with the booking JSON; the UI then calls /api/booking/confirm.
    7. Any thrown error goes to errorHandler and comes back as { error: { code, message } }.

    You migrated from Next.js + TypeScript to React + Express in JavaScript. How did you do it safely?Advanced▸
    1. Kept the contracts: same API paths, request/response shapes and error codes, so the UI logic barely changed.
    2. Stripped types automatically with a tool (ts-blank-space) that removes TypeScript syntax but keeps comments and layout, then fixed what it couldn't handle by hand.
    3. Replaced Next-only features: route handlers → Express routes; server components → React Router loaders; next/link → Link; next/image → a small Photo component.
    4. Re-ran every test: 21 unit tests, new API tests, and the full browser journeys on desktop and mobile. That caught real issues, such as a leftover fill prop and a 404 route warning.
    5. Committed as moves (git mv-style renames), so each file's history is preserved.
    6. Tested a fresh clone following the setup guide before pushing.

    client/src/router.jsx · client/src/pages/
    What is a loader, and why use loaders instead of useEffect + fetch?Intermediate▸

    A loader is a function React Router calls before rendering a route; the component reads the result with useLoaderData().

    export async function loader() {
  const [{ theaters }, { locations }] = await Promise.all([
    apiFetch("/api/theaters"), apiFetch("/api/locations"),
  ]);
  return { theaters, locations };
}
export function Component() {
  const { theaters, locations } = useLoaderData();
  ...
}

    Compared with fetching in useEffect:

    • No "loading → data" flicker inside every page, and no loading/error state boilerplate.
    • Data and page code load in parallel (with lazy).
    • If a loader throws, the route's errorElement shows automatically.
    • No race conditions when users click quickly between pages; the router cancels stale loads.
    client/src/pages/home-page.jsx
    How do errors and 404s work in the React app?Intermediate▸
    • Unknown URLs match the path: "*" route, which renders <NotFoundView/>.
    • If a loader fails (for example the API is down), the nearest errorElement (ErrorPage) renders inside the layout, so the header and footer stay. It offers "Try again", which calls navigate(0) to re-run the loader.
    • For a missing booking, the confirmation loader converts the API's 404 into throw data("Booking not found", { status: 404 }); ErrorPage checks isRouteErrorResponse(error) && error.status === 404 and shows the 404 view.
    client/src/pages/error-page.jsx · client/src/pages/confirmation-page.jsx
    How did you manage state in the 9-step booking wizard?Basic▸

    One useReducer holds the whole booking: step, date, guests, theatre, slot, customer, occasion, cart, coupon, payment method and pending booking. Steps dispatch actions like SELECT_THEATER or SET_CART_ITEM.

    Why useReducer over many useStates? The transitions are related: changing the date must clear the selected slot and theatre; lowering guests may clear a theatre that no longer fits. A reducer keeps those rules in one pure function:

    case "SET_DATE":
  return action.date === state.date ? state
    : { ...state, date: action.date, startTime: null, theater: null, slot: null };

    No Redux needed: the state belongs to one page.

    client/src/components/booking/booking-state.js
    How does the wizard survive a page refresh?Intermediate▸

    State is saved to sessionStorage in a useEffect on every change, and restored with useReducer's lazy initialiser, so the very first render already shows the restored step (no flicker):

    const [state, dispatch] = useReducer(wizardReducer, null, () => {
  const fresh = createInitialState({ today, ...prefill });
  return prefill.fromLink ? fresh : (loadStoredState(today) ?? fresh);
});

    sessionStorage (not localStorage) because a half-finished booking belongs to that tab. Storage access is wrapped in try/catch because it can throw in private mode. A draft from a previous day resets its date and slot.

    client/src/components/booking/booking-wizard.jsx
    Why React Hook Form? Controlled vs uncontrolled inputs?Basic▸
    • Controlled: React state holds the value (value + onChange), so it re-renders on every keystroke.
    • Uncontrolled: the DOM holds the value; you read it when needed.

    React Hook Form uses uncontrolled inputs, so typing doesn't re-render the whole form. With zodResolver, the same Zod schema from @luxe/shared validates the form in the browser and the request on the server.

    useForm({ resolver: zodResolver(customerSchema), defaultValues: state.customer })
    Why useWatch instead of watch() in the occasion step?Intermediate▸

    The React Hooks ESLint rules (which include React Compiler checks) flag watch() as incompatible: its return value can't be memoised safely. useWatch({ control, name: "occasion" }) is a proper hook that subscribes to one field, so the component re-renders only when the occasion changes. I use it to show occasion-specific fields (age for birthdays, partner name for anniversaries).

    How does the slot-availability hook avoid race conditions?Intermediate▸

    If the user changes the date quickly, an older request could finish after a newer one and show the wrong day's slots. useAvailability prevents it two ways:

    1. An AbortController cancels the previous request in the effect cleanup.
    2. Each result is stored with a key (location|date); the hook only returns data whose key matches the current inputs.
    client/src/components/booking/use-availability.js
    What does <StrictMode> do? Why do effects run twice in development?Basic▸

    In development, StrictMode deliberately mounts, unmounts and re-mounts components and runs effects twice, to expose missing cleanup (for example a timer or a fetch that isn't cancelled). That's why every effect in the app returns a cleanup: the slideshow clears its interval, the availability hook aborts its request, and keyboard listeners are removed. It has no effect in production.

    4. JavaScript

    Language questions, answered with code from this project.

    Why plain JavaScript? How do you keep it safe without TypeScript?Basic▸

    Plain JS keeps the code simple to read and run with no compile step. To compensate for the missing type checks:

    • Zod validates all data at the boundaries: every API request body and query, and every form.
    • JSDoc comments document the shapes of important inputs (pricing, planner), and editors show them on hover.
    • Tests (28) cover the business rules and API validation.
    • ESLint catches unused variables, hook mistakes and undefined names.

    Honest trade-off: TypeScript would catch more mistakes at compile time, such as a misspelled property, especially as the team grows.

    What are ES modules? Why do server imports end in .js?Basic▸

    ES modules use import/export (instead of CommonJS require). Every package has "type": "module". In Node.js, relative imports must include the file extension:

    import { createApp } from "./app.js";   // Node needs ".js"

    Vite (the frontend) resolves extensionless imports and the @/ alias for you, so client code can write import { cn } from "@/lib/utils".

    What is async/await? What does Promise.all do?Basic▸

    async/await is syntax for working with Promises without nested callbacks. Promise.all runs independent tasks in parallel:

    // home page loader: both requests happen at the same time
const [{ theaters }, { locations }] = await Promise.all([
  apiFetch("/api/theaters"), apiFetch("/api/locations"),
]);

    If any task rejects, Promise.all rejects. Promise.allSettled waits for all results regardless.

    What do ?. and ?? do?Basic▸
    • Optional chaining ?. stops and returns undefined if the left side is null/undefined: error?.code.
    • Nullish coalescing ?? gives a default only for null/undefined (unlike ||, which also replaces 0 and ""):
    const port = Number(process.env.PORT ?? 4000);
return error?.code ?? "INTERNAL_ERROR";
    Explain the custom error class ApiError.Intermediate▸
    export class ApiError extends Error {
  constructor(status, code, message, details) {
    super(message);
    this.name = "ApiError";
    this.status = status; this.code = code; this.details = details;
  }
}
throw new ApiError(409, "SLOT_UNAVAILABLE", "Sorry, this slot was just booked.");

    Services throw it for expected failures; the error handler checks error instanceof ApiError and sends its status and code. Anything else is an unexpected bug: it's logged, and the client gets a generic 500 (no internal details leak).

    server/src/lib/errors.js
    Your db.js exports a Proxy. Why?Advanced▸

    I wanted services to write prisma.booking.findMany() as usual, but without creating the database client at import time. A Proxy intercepts property access and creates the real client on first use:

    export const prisma = new Proxy({}, {
  get(_target, property) {
    const value = getClient()[property];          // created lazily, once
    return typeof value === "function" ? value.bind(getClient()) : value;
  },
});

    Benefit: the API tests import the whole app and test validation with no database, and a missing DATABASE_URL gives a clear message only when a query actually runs.

    server/src/lib/db.js

    5. Node.js & Express

    The backend: middleware, routing and error handling.

    What is middleware in Express? List yours in order.Basic▸

    Middleware is a function (req, res, next) that runs during a request; it can change the request/response, end the request, or call next(). Order matters. In app.js:

    1. Security headers (nosniff, DENY framing, referrer policy)
    2. cors(): allows only the configured frontend origin
    3. express.json({ limit: "100kb" }): parses JSON bodies
    4. Per-route: rate limiter, Cache-Control headers
    5. The /api router
    6. notFoundHandler for unknown /api paths
    7. errorHandler (last)
    server/src/app.js
    How does error handling work in Express 5?Intermediate▸

    An error-handling middleware has four parameters (err, req, res, next); Express recognises it by that count, which is why next stays even though it's unused. In Express 5, if an async route throws or its promise rejects, Express forwards the error to this handler automatically. In Express 4 you needed a wrapper or try/catch + next(err) in every route.

    if (error instanceof ApiError)   → its status + code
if (error instanceof z.ZodError) → 400 VALIDATION_ERROR + field errors
if (error.type === "entity.parse.failed") → 400 INVALID_JSON
otherwise                        → log it, 500 INTERNAL_ERROR

    Why are route handlers so short? What's the service layer?Intermediate▸
    api.post("/booking", perMinute("booking", 10), async (req, res) => {
  const booking = await createBooking(createBookingSchema.parse(req.body));
  res.status(201).json({ booking });
});

    Routes only handle HTTP: validate input, call a service, send a status. The services (src/services/) contain business logic and database access, with no req/res. That separation means the logic could be reused by a CLI, a job or a different framework, and is easier to test.

    What does app.set("trust proxy", 1) do?Intermediate▸

    On Render (or behind any load balancer), the request reaches Express from the proxy, not the user. With trust proxy, Express reads the real client IP from the X-Forwarded-For header into req.ip. Without it, every user would share the proxy's IP and the rate limiter would block everyone together.

    How are environment variables loaded on the server?Intermediate▸

    server/prisma/load-env.js uses dotenv to load server/.env.local then server/.env. Paths are resolved from the file itself (import.meta.url), so it works whether you run commands from the root or the server folder. It's imported first in index.js and in prisma.config.js, so the app and the Prisma CLI read the same settings.

    What is graceful shutdown, and did you implement it?Intermediate▸

    When the host stops the process (deploy, scale-down, Ctrl+C), it sends SIGTERM/SIGINT. Graceful shutdown stops accepting new requests, lets in-flight ones finish, and closes the database pool:

    process.on(signal, () => {
  server.close(async () => { await disconnect(); process.exit(0); });
});
    server/src/index.js
    Why separate createApp() from listen()?Basic▸

    app.js builds and returns the Express app; index.js starts listening on a port. Tests import createApp() and send requests with Supertest directly, without opening a real port, so tests are fast and don't clash with a running server.

    Why store money as integers in paise?Basic▸

    Floating-point numbers can't represent many decimals exactly: 0.1 + 0.2 === 0.30000000000000004. Storing ₹1,499 as 149900 paise keeps all arithmetic exact. Formatting to rupees happens only for display (formatINR).

    "Money is integer paise end to end, the same approach Stripe and Razorpay use."
    Why does CartItem store optionName and price when it links to AddOnOption?Intermediate▸

    It's a snapshot. If the "1 kg" cake later changes from ₹1,149 to ₹1,299, an existing receipt must still show what the customer paid. The foreign key keeps the link for reporting; the copied columns keep history accurate.

    How exactly does activeSlotKey prevent double booking?Advanced▸
    model Booking {
  activeSlotKey String? @unique   // "theaterId:slotId:2026-11-20" while holding the slot
  status        BookingStatus     // PENDING | CONFIRMED | CANCELLED | EXPIRED
}
    • A PENDING or CONFIRMED booking holds the key.
    • Expired or cancelled bookings set it to NULL; PostgreSQL allows many NULLs in a unique column.
    • Two concurrent inserts with the same key: one wins, the other gets a unique violation (P2002) → 409.

    Why not a unique index on (theaterId, slotId, date)? Then a cancelled booking would block the slot forever. A partial unique index (WHERE status IN (...)) would also work, but Prisma's schema can't express it. The nullable key gives the same guarantee natively.

    What does the seed script do? What does idempotent mean?Basic▸

    It loads sample data: 5 locations, 6 theatres, 24 slots, 12 add-ons (23 options) and 4 coupons. Idempotent means running it twice gives the same result as once: it uses upsert keyed on natural keys (slug, code), so re-running updates rows instead of duplicating them.

    server/prisma/seed.js · server/src/data/catalog.js
    What is a transaction, and where do you use one?Intermediate▸

    A group of queries that all succeed or all roll back.

    • Create booking: release lapsed holds on the slot key, then insert the booking.
    • Confirm payment: mark the booking PAID and increment the coupon usage. If the coupon is exhausted, throw, and the booking update rolls back too.
    await prisma.$transaction(async (tx) => {
  await tx.booking.updateMany({ where: { activeSlotKey: key, status: "PENDING", ... },
                                data: { status: "EXPIRED", activeSlotKey: null } });
  return tx.booking.create({ data: { ... } });
});
    What is the N+1 query problem? Does your code have it?Intermediate▸

    N+1 is loading a list (1 query) and then querying once per item (N queries). Availability avoids it: one query loads all theatres with their slots, one query loads all taken bookings for that date, and membership is checked in memory with a Set. Two queries, however many theatres there are.

    server/src/services/availability.js
    How do you handle dates and timezones? What bug did you hit?Advanced▸
    • The booking date is a calendar date (@db.Date), always an IST day.
    • "Today" is computed in IST (UTC+5:30): at 20:00 UTC on 31 Oct it's already 1 Nov in India, and a unit test checks that.
    • Slot start times use an explicit offset: new Date(`${date}T${time}:00+05:30`).

    The bug: in a manual test I expired a hold with SQL now() - interval '1 minute'. Prisma stores timestamps in UTC but my Postgres session was IST, so the value landed 5.5 hours in the future. Fixed with now() AT TIME ZONE 'utc'. Lesson: store UTC, convert only at the edges.

    shared/src/dates.js · shared/src/dates.test.js
    How is SQL injection prevented?Intermediate▸

    Prisma always sends parameterised queries: values travel separately from SQL text. The one raw query uses a tagged template, which is also parameterised:

    await tx.$executeRaw`
  UPDATE "Coupon" SET "usedCount" = "usedCount" + 1
  WHERE "id" = ${booking.couponId}
    AND ("usageLimit" IS NULL OR "usedCount" < "usageLimit")`;

    Never build SQL with string concatenation or use $executeRawUnsafe with user input.

    Which HTTP status codes do you return, and why?Basic▸

    What does an error response look like?Basic▸
    { "error": { "code": "SLOT_UNAVAILABLE", "message": "Sorry, this slot was just booked. Please pick another time." } }

{ "error": { "code": "VALIDATION_ERROR", "message": "Some fields are invalid.",
             "details": { "fieldErrors": { "customer": ["Enter a valid 10-digit Indian mobile number"] } } } }

    A machine-readable code for the frontend to branch on, a human message, and optional details. One errorHandler produces every error, so the shape never varies. The client's ApiClientError exposes status, code and fieldErrors.

    Why validate on the server if the form already validates?Basic▸

    Client validation is for user experience; server validation is for security. Anyone can bypass the browser with Postman or curl. Every body and query is validated with Zod in the route before touching the database, using the same schema as the form.

    Why recalculate the price on the server?Basic▸

    Never trust prices from the client. A user could edit the request to send total: 1. The booking API only accepts ids and quantities; it loads current prices from the database and computes the total itself.

    What is idempotency? Is your confirm endpoint idempotent?Advanced▸

    Idempotent means calling it many times has the same effect as once, which matters for payments because networks retry and users double-click.

    • If the booking is already CONFIRMED, confirm returns it unchanged.
    • Two simultaneous confirms: a conditional update (updateMany WHERE id = ? AND status = 'PENDING') lets only one win, so the coupon is counted once.

    With a real gateway I'd also store the gateway payment id with a unique constraint and accept an Idempotency-Key header.

    Walk me through the booking lifecycle.Intermediate▸
    POST /api/booking ──► PENDING (holds slot, holdExpiresAt = now + 10 min)
                          │
      ┌───────────────────┼─────────────────────────────┐
      │ confirm FAILURE   │ confirm SUCCESS              │ 10 min pass
      ▼                   ▼                              ▼
 PENDING + payment     CONFIRMED + PAID               EXPIRED (slot key → NULL)
 FAILED (retry OK)     (coupon redeemed)               confirm → 410 HOLD_EXPIRED

    Expiry is lazy: availability treats elapsed holds as free, the receipt reports them as EXPIRED, and the next booking on that slot releases them inside its transaction.

    How are coupons validated?Intermediate▸

    evaluateCoupon() in shared/src/pricing.js checks, in order: active → started → not expired → usage limit → minimum order. Then:

    • PERCENT: subtotal × % / 100, capped at maxDiscount;
    • FLAT: fixed amount;
    • rounded down to whole rupees, never more than the subtotal.

    Example: LUXE10 on ₹6,696 → ₹669.60 → capped at ₹500. Usage is only counted on confirmed payment, atomically.

    How does rate limiting work, and what are its limits?Intermediate▸

    A fixed-window, in-memory counter per route + client IP, as Express middleware. Limits per minute: booking 10, coupon 20, confirm 20, planner 30, waitlist 5, contact 5. Over the limit → 429 with Retry-After. An API test checks the sixth waitlist request gets 429.

    Limitation: counters live in one process's memory. With several server instances, each counts separately; production should use Redis.

    server/src/lib/rate-limit.js · server/src/app.test.js
    What's the booking reference format, and why not show the database id?Basic▸

    References look like LXS-H28S5FFE: 8 characters from an alphabet without 0/O and 1/I, so they're easy to read over the phone, generated with crypto.randomInt. The internal id is a long, unguessable cuid, used in the receipt URL so people can't guess other bookings' links.

    Why do some GET endpoints send Cache-Control headers?Basic▸
    • Catalogue endpoints (theatres, locations, add-ons) send public, max-age=300: they rarely change, so browsers and CDNs can reuse them for 5 minutes.
    • /api/slots and receipts send no-store: stale availability would cause failed bookings.

    8. AI Experience Planner

    Expect "is it really AI?". Answer confidently and honestly.

    Is the AI planner real AI?Basic▸

    Be honest: no. It's a deterministic, rules-based recommendation engine, and the README says so. Chosen on purpose: no API key or cost, same input → same output (unit-testable), and it explains itself with reasons like "Cosy, intimate room suited to the occasion".

    "It's a scoring engine, not an LLM. For a booking flow I wanted predictable, testable, free recommendations. An LLM could add natural-language input later, with this engine as the fallback."
    How does the scoring algorithm work?Intermediate▸
    1. Filter out theatres that can't fit the group.
    2. Score each theatre:
      • Capacity fit: up to 40 points, best when the room is ~75% full.
      • Occasion mood: intimate occasions get +20 for rooms of 6 or fewer; party occasions +12 for rooms of 8 or more.
      • Budget fit: up to 25 points when the theatre uses ~65% of the budget; −50 if over budget.
      • Rating bonus.
    3. Build a package from occasion-specific preferences.
    4. Return the top recommendation plus 2 alternatives.

    It lives in shared/, but only the server runs it (POST /api/planner), with the real catalogue.

    shared/src/planner.js · server/src/services/planner.js
    A unit test caught a bug in your planner. What was it?Advanced▸

    My first package builder was greedy: per category it took the most expensive option that fit. With ₹5,000 for a proposal it chose Premium decor and a cake and had nothing left for a gift. The test expected DECOR + CAKE + GIFT and failed.

    Fix: two passes. First secure one item per category at its cheapest option, then upgrade in priority order with the money left.

    "Greedy algorithms can be locally optimal but globally bad. The test caught it before any user did."
    How would you add a real LLM?Advanced▸
    • Let users type freely ("surprise 30th birthday for my wife, around ₹8k").
    • Call an LLM with tool calling, where the tool is the existing planExperience() over the real catalogue, so it can't invent theatres or prices.
    • Validate its output with Zod; on failure or timeout, fall back to the rules engine.
    • Keep the API key on the server, rate-limit and cache.

    9. Security

    What you protected, and what's still missing.

    How do you protect secrets like the database password?Basic▸
    • Secrets live in server/.env, which is git-ignored. Only .env.example files with dummy values are committed.
    • The database password exists only on the server. The browser never talks to the database.
    • In production, secrets go in the hosting dashboards (Render, Vercel).
    • Before pushing I checked tracked files for secrets and replaced a real local password used as a doc example.
    Are VITE_ environment variables secret?Intermediate▸

    No. Vite copies every VITE_* variable into the JavaScript bundle at build time, so anyone can read them in the browser. That's why the client has only VITE_API_URL (a public URL). Secrets must never be put in client env variables; they belong on the server.

    What is CORS, and how did you configure it?Intermediate▸

    Browsers block a page from reading responses from a different origin (domain/port) unless the server allows it with Access-Control-Allow-Origin. In production the website (Vercel) and API (Render) are different origins, so the API uses the cors middleware with an allow-list from CLIENT_ORIGIN:

    const allowed = (clientOrigin ?? "http://localhost:5173").split(",").map((o) => o.trim());
app.use(cors({ origin: allowed }));

    An API test confirms the configured origin is allowed and a random one isn't. Note: CORS protects browsers; it doesn't stop curl or Postman, which is why validation and rate limiting still matter.

    How are XSS and SQL injection prevented?Basic▸
    • XSS: React escapes everything rendered with {value}, so a name like <script> shows as text. I never use dangerouslySetInnerHTML.
    • SQL injection: Prisma uses parameterised queries, including the one tagged-template raw query.
    • Zod also limits input lengths, and express.json limits bodies to 100 KB.
    What security headers did you add?Intermediate▸
    HeaderProtects against
    X-Content-Type-Options: nosniffMIME-type sniffing
    X-Frame-Options: DENYClickjacking (being embedded in an iframe)
    Referrer-Policy: strict-origin-when-cross-originLeaking full URLs to other sites

    Set by Express on the API and by vercel.json on the website. I also disabled X-Powered-By so the API doesn't advertise Express. Next step: a Content-Security-Policy (or the helmet package).

    Can someone see another person's booking?Intermediate▸

    The receipt URL uses an unguessable cuid, so you'd need the exact link, but anyone with the link can view it. That's acceptable for a demo receipt. In production I'd add authentication (or require the booking email/phone) and check ownership on the server. Accessing other users' records by id is called IDOR.

    The GitHub repo already had a commit. How did you push without force?Intermediate▸

    GitHub had created an "Initial commit" with a one-line README. Force-pushing would have deleted it. Instead I fetched it and replayed my commits on top:

    git fetch origin
git rebase -X theirs origin/main
git push -u origin main      # fast-forward, no --force

    I made a backup branch first and checked the final files were identical (0-line diff). Merge vs rebase: merge keeps both histories plus a merge commit; rebase rewrites commits onto a new base for a linear history. Never rebase commits others already pulled.

    14. System design & scaling

    How would you integrate a real payment gateway like Razorpay?Advanced▸
    1. POST /api/booking creates the PENDING hold, then a gateway order on the server for the server-computed amount.
    2. The frontend opens the gateway checkout with that order id.
    3. The gateway calls our webhook; we verify its signature, then run the existing confirm logic.
    4. Never trust the browser's "success" callback alone.
    5. The unique paymentRef makes duplicate webhooks idempotent.
    6. If payment succeeds after the hold expired, refund automatically.
    How would you expire holds without lazy expiry?Advanced▸

    A scheduled job (Render cron job or a queue worker) every minute:

    UPDATE "Booking" SET status='EXPIRED', "activeSlotKey"=NULL
WHERE status='PENDING' AND "holdExpiresAt" <= now();

    The (status, holdExpiresAt) index makes it fast. Keep the lazy checks too, so correctness doesn't depend on the job.

    The site goes viral. What breaks first?Advanced▸
    • The website is static files on a CDN: fine.
    • The API: run several instances behind a load balancer; move rate limiting to Redis.
    • Availability endpoint (hottest): short cache (5–10 s) per location+date, read replicas.
    • Database connections: a connection pooler.
    • Booking writes: the unique constraint stays correct under any load.
    • Observability: metrics, tracing and alerts to find the real bottleneck.
    Optimistic vs pessimistic locking: which does your design use?Advanced▸
    • Pessimistic: lock the row first (SELECT … FOR UPDATE); others wait.
    • Optimistic: don't lock; detect conflicts when writing.

    Mine is optimistic: insert and let the unique constraint reject conflicts; confirm uses updateMany … WHERE status='PENDING' and checks count. That suits low contention, which is our case.

    15. Fundamentals freshers must know

    General questions, answered with examples from this project.

    What happens when you type a URL and press Enter (for this app)?Basic▸
    1. DNS resolves the domain; a TCP + TLS connection opens.
    2. Vercel's CDN returns index.html and the JS/CSS bundles.
    3. React starts; React Router matches the URL and runs the page's loader.
    4. The loader calls the Express API, which queries PostgreSQL and returns JSON.

    GET vs POST? PUT, PATCH, DELETE?Basic▸
    • GET reads, has no body, is safe and cacheable: GET /api/slots.
    • POST creates or performs an action: POST /api/booking.
    • PUT replaces, PATCH partially updates, DELETE removes.
    What is REST?Basic▸

    An API style built around resources in URLs (/api/booking), standard HTTP methods, meaningful status codes, and stateless requests (each carries everything the server needs). JSON is the usual format. The Express server is a REST API.

    SQL vs NoSQL: why SQL here?Basic▸

    The data is relational (theatre → slots → bookings → items) and needs constraints and transactions (no double booking; payment + coupon together). NoSQL suits flexible documents or massive horizontal scale where joins and transactions matter less.

    What is a JOIN? Primary key vs foreign key vs unique key?Basic▸
    SELECT b.reference, t.name AS theatre, b.total / 100 AS total_rs
FROM "Booking" b JOIN "Theater" t ON t.id = b."theaterId"
WHERE b.status = 'CONFIRMED';
    • Primary key: unique row id (Booking.id).
    • Foreign key: references another table (Booking.theaterId → Theater.id).
    • Unique key: no duplicates in that column (Coupon.code, Booking.activeSlotKey).

    Authentication vs authorization? JWT vs session?Basic▸
    • Authentication: who are you? Authorization: what may you do?
    • Session: the server stores session data; the cookie holds an id. Easy to revoke.
    • JWT: a signed token with claims; the server stores nothing. Harder to revoke.

    Not in this project yet. I'd add HttpOnly session cookies (with credentials in CORS) and check booking ownership on the server.

    What is a race condition? Give an example from this project.Intermediate▸

    A bug where the result depends on the timing of concurrent operations.

    • Server: two users booking the same slot at once. Solved with the unique constraint.
    • Client: an old availability response arriving after a newer one. Solved with AbortController and a request key.
    What is the Node.js event loop, in simple terms?Basic▸

    Node runs your JavaScript on one thread. When code awaits something slow (a database query, a network call), Node hands it off and keeps serving other requests; when the result is ready, the callback or await continues. That's why one Express server can handle many requests at once, as long as you don't block the thread with heavy synchronous work.
